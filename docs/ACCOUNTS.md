# Аккаунты и вход в Delta

## Пользовательский сценарий

Сайт показывает вход и регистрацию. Администратор после входа видит существующий
Control Center, обычный зарегистрированный аккаунт — экран ожидания доступа.
Это серверное ограничение: роль pending не может читать историю, устройства,
задачи, рабочие пространства или выполнять команды. Общее пользовательское
пространство пока не разделяется на владельцев: оно доступно только администратору.
Дизайн и возможности обычных пользователей будут разработаны отдельно.

Логины: 3–64 символа, латиница/цифры/точка/дефис/подчёркивание, регистр не учитывается.
Пароль: 10–128 символов. При регистрации нельзя передать роль или статус.
Первый admin создаётся оператором, не публичной регистрацией. Публичного
назначения администратора, восстановления пароля, MFA и почтовых уведомлений пока нет.

## Хранение и API

Core владеет account_users и account_sessions, миграция 0006. Tasks не получает
доступ к этим таблицам: браузер обращается к Core /api/v1/task-proxy/tasks,
Core проверяет сессию и вызывает Tasks по HTTP с внутренним DELTA_TOKEN.
Gateway /tasks-api/api/v1 также направляется в авторизованный Core proxy.
Tasks и PostgreSQL не следует публиковать напрямую в сеть.

Пароли хешируются scrypt (случайная 128-битная соль, N=16384,r=8,p=1).
Случайные сессии имеют 384 бита энтропии; в БД сохраняется только SHA-256.
Веб-сессия живёт 24 часа, cookie HttpOnly/SameSite=Strict, Secure при HTTPS.
Изменяющие запросы с cookie требуют X-Delta-Request: 1; CORS не открывается.
На login/register/agent-login действует общий лимит 10 попыток в минуту на IP
в памяти процесса. Для нескольких workers/реплик нужен общий limiter;
текущая установка использует один worker.

POST /api/v1/auth/register — username/password, новый pending-аккаунт.
POST /api/v1/auth/login — username/password, cookie и публичные поля аккаунта.
GET /api/v1/auth/me — текущая веб-сессия, без password_hash/секретов.
POST /api/v1/auth/logout — отзывает текущую сессию и удаляет cookie.
POST /api/v1/auth/agent-login — admin username/password, отдельная agent-сессия.

Агент входит по логину/паролю. Пароль не сохраняется. Сохраняется agent-сессия
на 30 дней в приватном settings.json (пока без OS keychain). Она не подходит
для HTTP административного API. WebSocket проверяет роль и сессию при подключении
и каждом сообщении/heartbeat: отозванное подключение закрывается. Выйти из
аккаунта и просто отключить компьютер — разные действия. Истечение сессии
останавливает переподключение и предлагает повторный вход.

## Развёртывание и первоначальный администратор

Установите DELTA_ACCOUNTS_ENABLED=true у Core. Compose включает это по умолчанию.
В тестах/старом CLI-окружении без флага остаётся прежняя development-token схема;
не используйте такой режим для новой пользовательской установки.
DELTA_TOKEN теперь только внутренний сервисный секрет. Не вводите его в сайт или GUI Agent.

Примените alembic upgrade head. Затем создайте admin через
`python -m delta_core.accounts.bootstrap`, передав пароль через stdin из приватного
файла (не аргумент командной строки). Команда требует DATABASE_URL именно Core,
отказывается менять существующего admin и не печатает пароль. Оператор может
использовать интерактивный getpass в доверенном локальном скрипте.

На целевом Nobara сервере включены аккаунты, миграция применена, admin создан.
Пароль передан владельцу отдельным локальным файлом, не добавлен в Git/логи.
Старый серверный CLI Agent получил отдельную admin agent-сессию в приватном
.runtime/server-agent-session. После 30 дней её нужно заменить новым входом;
настольный клиент предлагает повторный вход сам. Настройки OpenRouter и данные
существующего проекта сохранены. Резервные копии изменённых файлов и .env находятся
в .runtime/accounts-backup. Откат схемы не нужен для отката приложения: не удаляйте
таблицы аккаунтов или остальные данные без резервной копии.

Текущий адрес HTTP предназначен только для доверенной LAN. HTTP не шифрует пароль
и cookie в сети. Для внешнего доступа настройте HTTPS и корректную передачу схемы
reverse proxy; это также требуется для браузерного микрофона. Не отключайте
проверку TLS-сертификатов в агенте.

полный старый набор в режиме аккаунтов не заявляется проверенным.


### Настольный интерфейс

Agent-сессия дополнительно разрешает только `GET /api/v1/desktop/devices` и
`POST /api/v1/desktop/message` (message/device_id — та же валидация, что у веб-чата).
Оба пути проверяют срок, отзыв и роль admin; остальные HTTP API по-прежнему
не принимают Agent bearer. Чат использует зарегистрированные инструменты Core.
Настройки подключения и разрешения находятся в отдельном окне клиента.


## Палитра Delta

Веб-интерфейс и настольный клиент используют только чёрный, белый и нейтральные
оттенки серого. Это относится к логотипу и иконке, входу/регистрации, кнопкам,
выделению текста, фокусу, чату, голосовой анимации, настройкам и диагностике.
Статусы и ошибки различаются текстом и формой, а не цветными акцентами.
