# Контекст диалога Assistant

## Исправленная причина

Ранее `assistant_history` использовалась только для отображения. Каждый вызов LLM
содержал system + последнее user-сообщение: предыдущая задача и её UUID терялись.
Теперь `assistant/context.py` читает завершённые взаимодействия из Core DB перед
маршрутизацией. Текстовый и голосовой endpoints используют один AssistantService.

История передаётся стандартными ролями `user`, `assistant` (tool_calls), `tool`,
`assistant` (итог). Исторические вызовы получают уникальные ID; они не поступают
в исполнитель повторно. Старые результаты являются данными, а не инструкциями.
Предыдущие ответы модели сами по себе не считаются доказательством выполнения.

Окно: до 12 последних взаимодействий и 30 000 символов сериализованных сообщений.
Большие строки и списки сокращаются; для списков задач сохраняются прежде всего
ID, название, статус, приоритет, workspace и срок. История загружается из БД,
поэтому переживает перезагрузку страницы и перезапуск Core. Текущий MVP использует
единый диалог одного пользователя, как существующая страница истории; отдельные
пользователи/чаты потребуют отдельного conversation ID. Это не бессрочная память.

## Локальные ссылки на задачи

`ConversationIntentRouter` оборачивает обычный LocalIntentRouter:

- «Создай задание номер 6» → «Удали задание номер 6»: уникальное точное название,
  включая случай, когда слово «задание» входит в само название.
- «Заверши её», «Удали это задание», «Переименуй её в Отчёт»,
  «Поставь ей высокий приоритет»: последний однозначный результат работы с задачей.
- «Заверши вторую»: порядок последнего детерминированно показанного списка,
  а не текущий порядок ответа Tasks или предполагаемый числовой ID.

Перед изменением задача проверяется через зарегистрированный `tasks.list`.
Core никогда не читает БД Tasks. Дубликаты названий, несколько возможных задач,
удалённая задача, неудачный результат или смена фокуса на другой объект приводят
к уточнению, а не случайной мутации. Произвольный естественный язык остаётся у LLM,
которая теперь получает предыдущие сообщения, уточнения и результаты.

Поиск через read-tool сам по себе не завершает команду на изменение: после поиска
ассистент продолжает до нужного действия. Если модель пишет об успехе без вызова
нужного инструмента, прямой запрос на действие получает явное сообщение, что оно
не выполнено; полезный уточняющий вопрос сохраняется. Успех проверяется по результатам
инструментов, а не по формулировке модели.

## Проверка 2026-10-17

На работающих Core/Tasks/OpenRouter:
1. Создано тестовое задание с уникальным номером и удалено по названию.
   Проверен UUID вызова `tasks.delete` и последующий HTTP 404.
2. Создана задача, переименована через «её», изменён приоритет через «ей».
3. Модель правильно назвала новое название без дополнительного чтения Tasks.
4. «Заверши её» изменило статус именно той же задачи на done.
5. Через Tasks API проверены title/priority/status; тестовые задачи удалены.

Локальные изменения заняли 0,03–0,07 s, ответ LLM о новом названии — 2,85 s
в одном проверочном прогоне (не SLA и не статистический benchmark).
Автотесты покрывают формат OpenRouter, сохранение после пересоздания сервиса,
текст → голос, уточнения, границы окна, неоднозначность, точные ID, отсутствие
повторной мутации и недопустимость фиктивного успеха.

Итоговый прогон: 203 backend-теста, 6 frontend unit, 30 Chrome-сценариев;
frontend production build успешен. Проект оставлен включённым.
